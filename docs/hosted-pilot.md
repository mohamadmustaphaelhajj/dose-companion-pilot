# Hosted personal pilot on Render

This package targets only `dose-companion-pilot`. The future public product remains deferred. It is prepared for deployment; a running Render service and scheduler have not yet been provisioned.

## Service

The root `render.yaml` defines one free Docker web service in Virginia (not a Canadian region), from `feature/independent-phone-use` in the pilot repository. Automatic deploys are disabled. The server uses Python 3.12 and Gunicorn 27.0.1, one worker and four threads. Only one extraction runs at once. Render supplies public HTTPS; port binding is internal to its proxy. This package is not a standalone TLS server.

Docker's build context is `server/`. Its allowlist copies only the runtime Python sources and dependency/configuration files. Local `.env`, keys, tests, logs and photos are excluded. Never upload the whole local workspace or place secrets in the Blueprint/Git.

Enter these in Render's environment settings:

- `OPENAI_API_KEY`: provider key, never sent to the phone.
- `OPENAI_MODEL`: the owner's already-tested model identifier.
- `RETENTION_POLICY=standard`: the agreed personal experiment policy, still disclosed before each upload.
- `BRIDGE_TOKEN`: generated by the Blueprint; this is the private pilot pairing credential. Transfer it privately to the phone's Cloud connection settings, never into a URL, Git file or chat message. Rotating it revokes previous access.

The shared bearer credential serves this single-user pilot. It does not implement public accounts or multi-user authorization. Three-second pacing, a single active extraction and bounded images limit load. These are not a dollar spending cap: provider billing controls remain necessary. Submission receipts live in one process for ten minutes, so restart/cold-start loses them; no exactly-once guarantee is made across restarts.

### Routes

| Route | Authentication | Function |
| --- | --- | --- |
| `GET /healthz` | None | Returns only `{"status":"ok"}`. No provider call, images or secret metadata. |
| `GET /v1/config` | Pairing token | Checks readiness and returns the retention notice without submitting images. |
| `POST /v1/extract` | Pairing token + explicit app consent | One bounded multi-photo reading, using the same parsing, receipt checks and OpenAI code as the USB bridge. |

Application and Gunicorn access logging of requests is disabled; model errors return bounded codes. Render can maintain platform-level request metadata. This is not a zero-retention or medical-data compliance claim. Provider retention approval is limited to the personal experiment. Reminders/history stay on the phone, and camera capture can continue while the service prepares.

## Warm-up schedule

Use an external scheduler independent of the Mac, phone and Render process. The desired timezone is `America/Toronto`, including daylight saving changes. Target `/healthz`, never `/v1/extract`:

- Lead-in requests at 10:55 and 22:55.
- Every five minutes during 11:00–11:55 and 23:00–23:55.
- Final requests at noon and midnight.

Equivalent cron expressions, **only on a scheduler configured for America/Toronto**, are:

```text
55 10,22 * * *
*/5 11,23 * * *
0 0,12 * * *
```

Alternatively run `server/warm_pilot.py` on an external Python 3.9+ scheduler every five minutes with `PILOT_BACKEND_URL=https://the-service.onrender.com`. It checks the Toronto window before issuing a content-free GET, avoids redirects and sends no credentials/photos. On platforms with UTC-only scheduling, this Python gate handles seasonal offsets. Do not run it inside the sleeping Render service: that cannot wake itself.

No external schedule is activated by these files. Activation needs scheduler setup and a real deployed URL. Warm-ups are best effort: scheduling delays, service restarts and free-tier suspension can still cause a cold start. Hosting and provider quotas still apply.

## Phone setup and acceptance

Set the real HTTPS address and pilot pairing token in the app's Cloud connection settings. The token field is hidden and that screen blocks screenshots. A readiness check shows “Preparing the label reader” while waiting; it can wait up to 90 seconds for the reply. Capture remains available, but upload stays disabled until readiness and explicit consent. Only metadata checks are involved; there is no automatic retry of an image submission.

Before declaring independent use complete:

1. Deploy the reviewed commit and verify `/healthz` over public HTTPS.
2. Verify that missing/wrong pairing credentials fail on both protected routes, and that the correct phone connection shows the retention notice.
3. Disconnect USB, close the Mac bridge, and check the service from the phone's Wi-Fi/mobile connection. A server readiness flag is not proof of funded API billing.
4. Test a real label only with the owner's explicit approval for the paid provider request. Preserve explicit field/dose confirmation.
5. Leave the service idle, verify startup feedback, and confirm selected photos remain available if a request fails. No automatic paid retry may occur.
6. Activate the external schedule and observe actual response times in both local windows.
7. Confirm offline reminders/history still work. Source publication alone does not install an update on the friend's phone.

## Validation status

The local and hosted backends share extraction code. Mocked tests cover authentication, content-free warm-ups, request limits, single-call multi-image extraction, error privacy, concurrency, duplicate IDs after an uncertain provider failure, and winter/summer schedule boundaries. No paid inference is needed for these checks.

On November 26, 2026, all 21 backend tests passed, including real HTTP through the WSGI adapter with a mocked model. The Lab app, instrumentation compilation and lint passed. The Samsung was not connected, so the changed startup guidance has not yet had a device run. No image upload to OpenAI or paid inference was performed.

The current Mac has Python 3.9 and no Docker runtime. WSGI behavior can be tested locally; the Python 3.12/Gunicorn container build still requires Docker or the Render build pipeline. Hosted network/phone acceptance and external scheduling remain pending deployment.
